# 2026-11-14 全长 LongChat：首 token 延迟（TTFT）

目的：检验论文 §7.3 / Fig. 8 的延迟结论。论文说 CacheGen 比量化基线快 3.2–3.7 倍，比传文本后重新计算快 3.1–4.7 倍。

运行：RTX 4090 D，提交 `d6b6626` 加未提交的 `tools/full_length_ttft.py`（SHA256 前缀 `210eee6347ac35e3`），用时约 10 分钟，退出码 0，共 160 条记录。下载文件的 SHA256 与服务器一致。统计由 [analyze.py](analyze.py) 生成，输出在 [summary.json](summary.json)。`pilot/` 是 1 篇文档的试跑：第一次解码时显存不够（`pilot-oom.log`），改成不同时保留两份解压结果后重跑通过。

## 方法

- **流程：** 与质量实验相同。KV 只覆盖上下文，乙端解压后现算问题的 KV，再出第一个 token。数据是 ID 0–19，不截断，KV 长度 8559–9288 token。
- **实测：** 解码时间（字节到 GPU 上的 KV，含反序列化），以及在解压后的 KV 上现算问题、出第一个 token 的时间。传文本的方案测的是从头计算上下文和问题、出第一个 token 的时间。每项先预热 1 次，再取 3 次的中位数，计时前后都同步 CUDA。
- **传输不实测，按带宽计算：** 传输时间 = 体积 × 8 ÷ 带宽。
  - **串行**：传输 + 解码 + 第一个 token，三步不重叠。
  - **理想流水**：max(传输, 解码) + 第一个 token，假设分块后传输和解码完全重叠，是下限。
  - 传文本：文本只有约 43 KB，传输时间可以忽略，所以与带宽基本无关。
- **质量：** 取自之前同样 20 篇、同样流程的质量实验，这里不再重跑。所有方法的第一个 token 都与重新计算的结果一致（20/20）。

## 判断

- **比量化基线快：** 和论文一致。相对 8 bit 快 2.6–3.6 倍，落在论文 3.2–3.7 倍区间附近；相对 4 bit 快 1.4–1.8 倍，与 Fig. 8(a) 估读的约 1.8 倍接近。论文文字和 Fig. 8 的对应关系有矛盾（见差异记录）：按图看，3.2–3.7 倍对应的是 8 bit。准确率都是 20/20，所以这是同质量下的加速；但等级 1 与原始回答逐字相同的篇数（6）略低于 4 bit（7）。
- **比传文本后重新计算快：** 取决于带宽。3 Gbps 时快 3.0 倍（理想流水 4.2 倍），落在论文 3.1–4.7 倍区间附近；10 Gbps 时快 5.4 倍；1 Gbps 时只快 1.35 倍；0.5 Gbps 时反而慢约 35%（2.72 对 2.02 秒）。传文本的 2.02 秒与之前从 Fig. 8(c) 估读的约 2.2 秒接近。
- **解码不是瓶颈：** 等级 1 解码约 0.19 秒，3 Gbps 时传输约 0.41 秒，所以带宽较低时延迟主要来自传输，体积直接决定延迟。

## 局限

- 传输是按带宽计算的，没有走真实网络，没有 TCP 开销和带宽波动。理想流水只是下限，当前实现并没有分块流水解码。
- 传文本的方案用的是本仓库为数值稳定加的分块线性层和显式因果掩码，可能比 FlashAttention 或 vLLM 慢，因此对 CacheGen 略有利。
- 只有 20 篇、一张 RTX 4090 D。论文用的 GPU 和带宽设置不同，倍数只能比大致范围。
- 质量列取自之前的实验，没有在这次计时中重新生成回答，只核对了第一个 token。
